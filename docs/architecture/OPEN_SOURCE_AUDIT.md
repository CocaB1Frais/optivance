# OPTIVANCE — Open-Source Audit

**Source audit date:** 2026-11-06  
**Decision/document alignment reviewed:** 2026-11-10  
**Scope:** Public upstream repository documentation, visible repository structure and license declarations; Microsoft platform documentation for Windows APIs and deployment.  
**Evidence labels:** “Verified” means stated in an upstream repository or official platform documentation. “Upstream claim” means a project’s own unverified feature or benchmark statement. “Recommendation” is an OPTIVANCE design conclusion.

## Current repository

At the initial source audit on 2026-11-06, the repository had no application source, build manifest, dependency list, tests or UI implementation. The Phase 0 Markdown documentation is present in the current repository. No application implementation exists to measure or reuse; this document does not describe the current documentation inventory as empty.

This is a documentation and upstream-evidence audit, not a line-by-line security review of each external codebase. Upstream test suites and benchmark figures were not run independently. No OPTIVANCE measurements exist.

## Cross-project conclusions

1. **Rust is a strong core candidate.** Several relevant projects already use compact arenas and bounded/concurrent scanning in Rust. This is evidence of a viable ecosystem, not proof that any one implementation meets OPTIVANCE’s correctness or idle-resource targets.
2. **An MFT fast path is feasible but is not one uniform technique.** FSCTL_ENUM_USN_DATA is an OS-managed enumeration API. Raw volume/$MFT readers parse on-disk structures directly. A USN change journal is a third, distinct mechanism intended to track changes. They have different data, privilege, correctness, and I/O trade-offs.
3. **A fallback directory walk remains mandatory.** It is needed for FAT32, exFAT, non-NTFS locations, individual folders, and inaccessible/unsupported raw volume paths.
4. **Every size needs an explicit meaning.** Logical EOF, allocation size, directory rollup, and a physical-space estimate are different figures. Sparse, compressed, deduplicated, cloud-placeholder, reparse-point, and hardlinked data can make them diverge.
5. **A UI must virtualize both rendering and data delivery.** A renderer that draws one widget per file does not scale to millions of entries. Keep the canonical index in the engine and query only visible rows, aggregates, and treemap rectangles.
6. **License compatibility is not the only selection criterion.** Some permissively licensed projects still have implementation gaps, young MFT code, or additional README distribution statements. Audit exact license text, file-level headers, notices, and transitive dependencies before adding code.

## Open questions carried into architecture validation

- Maintained Windows 11 x64 is primary; Windows 10 Enterprise LTSC 2019 x64 is the secondary reference; LTSC 2021 remains conditional under active security support. Other Windows 10 exclusions are fixed in D-01. .NET 10 LTS self-contained x64 is selected; exact runtime-pack notices and installer signature remain to be reviewed.
- Which MFT backend meets the required coverage/correctness with acceptable resource cost? The approved privilege boundary is one-shot UAC only when a requested MFT scan requires it; no startup prompt or permanent service.
- Alternate Data Streams are excluded from ordinary totals; only consider separate metadata display if a selected backend reads them reliably. Hardlinks use all visible paths and one deterministic representative for aggregate weight; verify this behavior against backend results.
- Scan states and retention are approved; summaries retain status/errors, while partial paths persist only with detailed-inventory opt-in. SQLite is recommended pending technical validation of schema, migrations, purge and crash recovery.
- Which temperature and hardware metrics are available without vendor software or a kernel driver? Report unavailable metrics explicitly.
