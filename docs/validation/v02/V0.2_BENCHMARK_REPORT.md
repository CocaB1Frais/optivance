# OPTIVANCE V0.2 — Rapport de benchmark Storage

**Date :** 11 novembre 2026  
**Statut :** deux mesures terminées sur Windows 11 x64, volume NTFS `C:`  
**Périmètre :** analyse classique Rust appelée par `ScanEngineClient`; pas de MFT

## Environnement et protocole

- Hôte : Windows 11 x64, version 25H2, build `10.0.26200.9457` (la famille de build `26200` correspond à Windows 11 25H2 selon la [documentation de publication Microsoft](https://learn.microsoft.com/en-us/windows/release-health/windows11-release-information)).
- Volume : `C:`, NTFS, 255 832 952 832 octets. Le nombre de processeurs logiques visible au processus était 12. Le modèle de CPU, la mémoire physique et le modèle du disque n’ont pas pu être relevés dans le contexte d’exécution; ils ne sont donc pas supposés.
- Runtime de mesure : .NET SDK `10.0.404`, runtime `10.0.15`, Rust MSVC x64 `1.99.1`.
- Exécution sous un compte hors rôle Administrateurs (`isAdministratorRole=False`); aucune élévation UAC.
- Cible : `C:\` pour les deux passes V0.1 antérieures et les deux passes V0.2.
- Parcours en lecture de métadonnées seulement : aucun contenu de fichier lu, aucune écriture sur le volume, aucun accès MFT, aucune modification d’ACL et aucun vidage du cache Windows.
- Les avertissements n’ont été comptés que par nombre. Les journaux bruts temporaires ont été supprimés après extraction des métriques; aucun chemin local n’est conservé dans ce rapport.
- Le benchmark V0.2 a été exécuté par le probe jetable [ScanProbe](ScanProbe/Program.cs), qui réutilise `Optivance.Core` et `Optivance.Infrastructure`, sans dépendance NuGet.
- Reproduction après le build Release : `dotnet .\validation\v02\ScanProbe\bin\Release\net10.0-windows\ScanProbe.dll C:\`. L’échantillonnage du pic mémoire combiné prenait une mesure du processus .NET et du worker Rust toutes les 500 ms.

Le build `26200` est identifié par Microsoft comme Windows 11 version 25H2; la valeur `ProductName` de registre affichée sur l’hôte n’a pas servi à identifier la version. Les scans ont porté sur un volume actif et non sur un instantané : les entrées ont pu changer entre les passes.

La durée client moyenne passe de **81,610 s à 69,821 s**, soit **14,4 % de moins** dans ces mesures. Le CPU Rust moyen baisse d’environ **2,1 %**. Les pics mémoire combinés échantillonnés V0.2 sont **255,2 MB** et **210,9 MB**; leur moyenne (233,0 MB) est environ **23,1 %** sous la moyenne V0.1 (303,1 MB). L’écart de 44,3 MB entre les deux passes V0.2 montre que ce relevé mémoire par échantillonnage de 500 ms est instable; ne pas interpréter le pourcentage comme une mesure mémoire précise. Ce sont des observations sur cet hôte, pas des seuils d’acceptation produit.

Les comptes V0.2 dépassent les comptes V0.1 de 108 à 118 fichiers et de 105 dossiers. Le volume étant actif, les différences de contenu et d’accès empêchent une comparaison à instantané strict. Les tailles agrégées diffèrent aussi légèrement d’une passe à l’autre. Les avertissements V0.2 sont 591 contre 717 en V0.1; leur cause n’a pas été ventilée par chemin et une part peut venir des accès ou des changements du volume.

## Ce qui a changé

- Le protocole v2 transmet un index plat : identifiants, parents, plages d’enfants et noms, au lieu de répéter le chemin absolu de chaque entrée.
- Les entrées sont transmises par lots de 512; la taille de lot n’est pas un message individuel par fichier.
- Lecteur/écrivain Named Pipe tamponnés à 64 KiB; les sondages d’annulation et messages de progression sont moins fréquents.
- Les informations d’identité de fichier sont demandées en priorité pour les fichiers ayant plusieurs liens; `FILE_STANDARD_INFO` fournit la taille allouée et le nombre de liens. Les API Windows distinguent `AllocationSize` de `EndOfFile` dans [FILE_STANDARD_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info).
- L’interface conserve un index plat et construit seulement les lignes du dossier affiché; la grille est virtualisée et la disposition treemap est calculée hors du thread UI.

Les mesures montrent que le coût dominant reste celui des appels de métadonnées et d’informations par fichier. Ajouter des threads sans étude n’est pas justifié par ce seul résultat. Les résultats ne sont pas comparés à WizTree, ne démontrent aucune équivalence de performance et ne mesurent pas la treemap d’un dossier contenant des dizaines de milliers d’enfants.

## Limites et reproductibilité

- V0.1 n’exposait pas la même décomposition des phases; seule la durée, le CPU Rust échantillonné et la mémoire ont été conservés de la référence précédente. Il n’existe donc pas de comparaison avant/après pour le volume IPC ou les temps de phase.
- Le cache n’a pas été vidé. V0.1 comme V0.2 comportent deux passes naturellement chaudes; aucune mesure à cache froid n’est revendiquée.
- Le volume est vivant : comptes, tailles, avertissements et caches changent entre passes.
- Le probe mesure le chemin client/worker sans rendu WPF. Le pic mémoire d’une analyse complète pilotée par l’interface peut être supérieur.
- Un seul poste Windows 11 a été utilisé. Aucune preuve de compatibilité n’est produite pour Windows 10 Enterprise LTSC 2019/2021.
- Le scan classique n’est pas une preuve de l’accès MFT et ne valide ni les droits de la future voie MFT, ni l’exactitude sur les fichiers supprimés/concurrents, ni la gestion exhaustive des hardlinks.
- La formule des tailles allouées reste dépendante des métadonnées que Windows autorise à lire. Quand l’identité du fichier est inaccessible, un avertissement est émis et la déduplication du hardlink ne peut pas être garantie pour cette entrée.

### Verdict

**Amélioration mesurée, mais écart de performance restant important.** Les changements réduisent la durée moyenne observée de 14,4 %. Le pic mémoire échantillonné est inférieur en moyenne mais varie fortement entre passes; sa mesure reste indicative. La majeure partie du temps demeure dans les appels de métadonnées et d’informations par fichier. La voie MFT reste une étude séparée, jamais utilisée par ces mesures.
